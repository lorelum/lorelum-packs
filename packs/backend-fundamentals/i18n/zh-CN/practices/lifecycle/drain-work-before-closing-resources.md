## 何时应用

在接入终止信号、部署钩子、服务器关闭或清理回调时应用。围绕进程实际拥有的内容，安排工作接收、已接纳工作和依赖清理的顺序。仅关闭监听套接字并不能证明其所有工作均已完成。

## 指导

1. 识别现有的工作接收路径、已接纳工作和自行管理的依赖。仅在实际存在时，才纳入后台任务、定时回调、消费者或流。定义完成条件时，应包括每个工作单元所属的写入或确认。
2. 在部署允许的终止时限内设置关闭截止时间，并预留清理时间。如果工作无法安全停止，定义取消机制，以及未完成或强制终止时的结果。固定睡眠不等于排空，而等待超时也不会停止其底层操作。
3. 在有就绪机制时撤销就绪状态，并阻止定时器或消费者启动更多工作。依据部署策略选择 HTTP 工作接收的截止点：立即拒绝新工作，或仅在依赖仍可用、且关闭总截止时间仍允许完成工作和清理时，在有界的路由传播宽限期内继续服务。到达截止点后，即使路由仍在发送请求，也要在本地拒绝新工作。重复触发必须汇入同一个关闭操作。
4. 在预算内等待已接纳的工作，同时保持其依赖可用。对于框架跟踪的工作，使用框架的生命周期机制；对该生命周期之外的现有工作，则显式等待其结束。对长连接采用既有的完成或取消策略；套接字被中止并不能证明数据库写入已经停止。
5. 使用方都已完成或停止之后，按依赖顺序关闭自行管理的资源并等待关闭完成，在仍有需要时保持日志可用。到达截止时间时，使用已定义的终止结果，而不是关闭仍在运行的代码所依赖的资源，然后将其称为优雅排空。不要将被中断的工作报告为成功完成。

当此进程具备明确的停止接收、有界工作完成和依赖释放顺序，并包含如实描述的截止时间到达后的结果时，即可停止。

## 反模式

信号处理器并发关闭连接池和服务器，然后睡眠一段时间后退出。一个已接纳的发票请求执行到最后一次查询时，其连接池已经关闭。

## 原因

依赖的存活时间必须长于其使用方。停止接收新工作，为剩余工作划定边界；等待这些工作，保护已接纳的操作；设置截止时间，避免关闭无限期持续。它们各自应对不同的故障，任何一个都不能用延迟来替代。

## 例外与边界

没有后台工作的进程不需要任务注册表；没有就绪机制的进程可以直接停止接收新工作。使用现有生命周期设施，而不是另建一套平台。崩溃或强制杀死进程可能绕过钩子。被中断的数据变更结果不确定，因此仅靠关闭流程无法确立安全重放或持久交付。

## 示例

一个只有 HTTP 工作的 Fastify API 先退出路由，并到达选定的工作接收截止点，再启动 `app.close()`，同时保持连接池开放。`preClose` 可能在请求完成之前运行；连接池在 HTTP 工作排空之后于 `onClose` 中关闭，并遵守插件顺序。其协调器预留清理时间，如果有界排空无法完成，就使用部署的终止路径，既不声称被中断的请求已成功，也不承诺零停机发布。
