## 适用场景

当金额成为计费、余额、退款或结算的权威依据时应用。在数值流转的整个路径中保留精确含义；显示格式化无法修复近似误差或单位错误。

## 具体指导

1. 显式携带币种和单位，或通过强制执行的外围契约携带这些信息。从权威元数据或接收方 API 获取受支持的币种以及特定操作的最小货币单位规则。两位小数和某个提供方使用的计价单位都不是通用规则。
2. 使用精确十进制数，或以声明的最小货币单位表示并进行溢出检查的整数。根据允许的金额及中间计算选择精度、小数位数和范围。检查溢出，并在舍入前保留所需精度。不要把不同币种当作相同单位合并。
3. 将原始十进制文本或整数单位直接解析到该表示中，不经过中间二进制浮点数。拒绝非有限值、不支持的币种、超出范围的金额和超出精度的输入，除非该操作明确允许对这种输入舍入。
4. 确定舍入边界、目标小数位数和模式，包括负金额以及恰好处于中点的情况。避免反复舍入中间结果。声明了小数位数的 PostgreSQL `numeric` 会在赋值时舍入；确保这种强制转换符合业务契约。
5. 在驱动和序列化过程中保留精确性。JSON 数字不能保证各消费方精确处理十进制数或大整数。必要时定义十进制数字符串或整数字符串字段；以数字表示的最小货币单位必须落在每个参与方都能精确表示的范围内。接收方必须精确解析，而不能先转成浮点数。

当金额、币种和计价单位从输入经过存储直至输出都保持预期值，且仅在约定边界进行舍入时，即可停止。

## 反模式

一个服务使用二进制浮点数和硬编码的 100 来解析金额，然后发送超出 JSON 消费方精确范围的大额已存储整数。精确的数据库列无法恢复已经丢弃的小数部分，也无法恢复在序列化后改变的值。

## 原因

并非所有十进制数量都能由二进制浮点数精确表示。仅靠精确存储也无法防止币种单位混淆、非预期的小数位数强制转换，或跨语言的精度损失。

## 例外与边界

近似分析可以在误差被明确接受的情况下使用浮点数；这些值不能悄然成为付款指令。精确表示不会替你选择税务政策、汇率、分摊规则或价格。带小数的中间值可能合理地超出某一币种可支付的小数位数。

## 示例

退款契约接受 `{"currency":"USD","amount":"7.25"}`，其中金额是以主货币单位表示的十进制文本，并将其精确存储。支付适配器将它转换为 725 个最小货币单位。金额为 `"725"` 的 JPY 退款会转换为 725，而不是 72500。适配器使用其提供方的币种规则；当消费方无法用 JSON 数字保留大额已存储单位值时，这些值以字符串传输。
