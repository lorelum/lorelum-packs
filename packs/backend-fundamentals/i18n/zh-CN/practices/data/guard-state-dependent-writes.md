## 适用场景

当重叠执行的写入方可能使库存预留、带版本的编辑或允许的状态变更失效时应用。用事务包住分离的读取和写入，本身并不能保全先前的观察结果。

## 具体指导

1. 明确写入生效时必须成立的前置条件。将作业和管理路径也纳入竞争写入方。区分对已存储值做增量更新和替换旧快照。
2. 对于单行规则，优先使用一条条件语句。基于已存储的列计算增量变更，并在 `WHERE` 中加入数量或状态谓词。对于替换式编辑，比较预期版本，并在成功时推进版本；所有相关写入方都必须推进该版本。
3. 报告完成前，检查受影响行数或 `RETURNING`。针对单个目标的操作必须恰好匹配一行。零行表示前置条件或目标不匹配；返回既有的不可用、编辑已过期或冲突结果，而不是成功。
4. 对于跨越多行谓词的决策，使用覆盖该不变式的事务作用域锁或隔离级别。在决策前锁定现有行，并将保护保持到提交；以一致的顺序获取多个锁。锁定返回的行并不能预留缺失的行，也不能阻止所有竞争插入。
5. 将业务拒绝与死锁或序列化失败区分开。回滚失败的工作。如果现有策略允许重新启动失败的事务，应从新状态重新执行读取和决策；绝不能移除谓词、复用过期的替换值，或盲目重试已被拒绝的状态转换。不要在用户交互或远程调用期间持有锁。

当每次成功的变更都会强制执行其当前状态前置条件、竞争写入方共享该保护，且竞争失败不会被当作已完成变更返回时，即可停止。

## 反模式

两个结账请求都读到一件可用商品，计算出零，然后保存这个绝对值。两个订单都被接受。对每个请求使用普通的读已提交事务，并没有让其先前的观察变成独占。

## 原因

受保护的决策在数据库中协调，而不是依赖时序。在 PostgreSQL 的 Read Committed 隔离级别下，竞争更新会等待，并针对更新后的行重新检查自己的谓词。跨行规则需要覆盖更大决策范围的保护。

## 例外与边界

如果丢失期间发生的编辑是可接受的契约，那么无条件的“最后写入者获胜”替换可能是有意为之。唯一性、必需写入共享一次提交，以及重复事件处理是不同的保证。Repeatable Read 不是防止跨行异常的通用手段，而 Serializable 可能拒绝事务，并非悄然让每次尝试都成功。

## 示例

预留操作执行 `UPDATE inventory SET available = available - $1 WHERE sku = $2 AND available >= $1 RETURNING available`，数量已预先校验为正数。返回一行才允许成功；没有返回行时，产生既有的不可用结果。竞争失败方不会去掉数量保护条件后重试，而先前展示的可用数量绝不被当作预留。
