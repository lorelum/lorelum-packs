## 何时应用

当重新投递、并发工作进程、重启或确认丢失可能重复产生非幂等的本地数据库效果时应用。完成标记必须表示该消费者的效果已提交，而不只是某个工作进程收到了事件。

## 指导

1. 从经过身份认证的来源契约中派生稳定的事件键，按需要纳入必需的提供方、环境、账户或租户范围，以及消费者身份。使用非空组成部分和立即生效的数据库唯一性约束。投递尝试 ID、时间戳或资源 ID 不能与事件身份互换使用。
2. 在产生效果的事务中，以原子方式认领该精确键，例如使用 PostgreSQL 的 `INSERT ... ON CONFLICT (source_scope, consumer, event_id) DO NOTHING RETURNING event_id`。只有插入了标记的事务才执行效果。事先检查或对不存在的行执行 `SELECT ... FOR UPDATE` 并不能预留该键。
3. 通过同一个事务执行所有纳入保障的本地变更，并要求其成功条件成立。将标记与效果一同提交；任何处理失败都应同时回滚二者。绝不先提交处理中标记，也不在提交效果后再添加标记。
4. 仅将与保留的精确键发生冲突视为重复处理成功。并发插入会等待竞争事务：竞争事务提交后会阻止再次认领；竞争事务回滚后，该键仍可被认领。超时、中止以及不相关的约束失败仍然是失败。只有提交之后才能确认工作完成，不能在未提交的观察结果或未能获得锁之后确认。
5. 重放与恢复也遵循同一规则。在允许的重新投递时间范围内，保留可跨重启的持久证据，包括人工重放和积压恢复。在删除更早的标记前，应保留等价保护，或明确限制这些重放路径。

当一个带作用域的键最多允许一次已提交的本地效果、失败尝试不留下完成标记，且保留的证据可在重启或确认丢失后防护重新投递时，即可停止。

## 反模式

某工作进程提交已处理事件标记，随后在增加积分之前崩溃。重试会跳过缺失的效果。颠倒这两次提交的顺序，则可能增加两次积分。

## 原因

唯一性协调相互竞争的认领；共享事务将胜出的认领与已完成工作绑定。持久证据由此区分已提交的处理与失败尝试。

## 例外与边界

现有的天然幂等操作或业务约束可能已经足够。不同事件 ID 仍可能描述同一个业务动作；去重并不能解决顺序问题或更新丢失问题。

仅覆盖同一数据库中的效果。远程调用、另一个数据库以及消息代理确认不会随此事务回滚。不要声称能够保证远程恰好一次投递，也不要以围绕网络调用保持事务开启来替代集成实际的幂等性契约。

## 示例

某奖励消费者认领 `(partner_account_scope, consumer, event_id)`，增加一个账户的余额，并将二者一同提交。账户不存在时，一切都回滚。如果提交成功但确认丢失，重新投递会找到保留的标记并跳过增加操作，工作进程重启之后也一样。
