## 何时应用

当代码借出数据库客户端，或修改围绕该借出操作的成功、失败、提前返回或取消路径时应用。应确定在客户端可安全复用或必须丢弃之前，由谁拥有它。连接池容量规划属于另一项决策。

## 指导

1. 复用进程现有的连接池。对于独立查询，如果连接池的获取与释放辅助函数提供所需语义，应优先使用它；不要为每个请求创建一个连接池。
2. 每次成功借出连接后，使用现有资源 API 或 `try`/`finally`，建立一条作用域明确的清理路径。覆盖成功、异常、提前返回和取消。将一个事务中的所有语句保持在该已借出的客户端上执行。
3. 归还客户端之前，提交已完成的事务，或回滚未完成的事务。如果回滚失败或驱动报告连接已损坏，应通过受支持的驱动 API 丢弃它；绝不将不安全的事务或连接状态重新投入使用。
4. 仅在工作确实需要客户端时持有它。被放弃的连接获取等待仍可能在稍后交付客户端：应使用驱动的取消机制，或为这个迟到结果安排清理。调用方超时本身并不会归还连接。
5. 各个客户端完成工作后，应归还或丢弃。只有在使用共享连接池的工作已完成或停止后，才由其生命周期所有者关闭连接池，而不是在普通请求结束时关闭。

当每次成功获取连接在所有退出路径上都能安全归还或丢弃，且共享连接池不会在其使用者之前被关闭时，即可停止。

## 反模式

一次插入在执行 `release()` 前抛出异常。每个失败请求都消耗一个新的连接池槽位，而提出的修复却是增大连接池上限，而非修复所有权问题。

## 原因

连接池只能复用调用方归还的连接。清理也必须保留可复用的状态；归还已中止的事务或损坏的客户端，会将一个请求的失败传递给下一个调用方。

## 例外与边界

短生命周期的维护命令可以拥有一个直连连接，并可靠地将其关闭，而无需连接池。遵循实际部署驱动关于事务错误、丢弃、取消和会话状态的规则。可靠释放连接并不能确定部署容量，也不能约束获取等待；这些属于连接预算决策。

## 示例

某事务辅助函数获取一个客户端，在两次写入均成功后提交，并在失败时回滚。其 `finally` 会归还客户端，除非回滚失败，此时应丢弃客户端。请求从不调用 `pool.end()`；进程会在连接池使用者全部结束之后关闭该连接池。
