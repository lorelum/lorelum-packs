## 适用场景

当输入进入 SQL 时应用，包括 ORM 原始片段、报表排序、批量查询和存储过程内部的动态 SQL。队列消息、可编辑配置和先前存储的值仍然是数据；它们的来源不会使其成为可信的查询语法。

## 具体指导

1. 找到最终执行 API，将可变数据与结构选择分开。名称、日期、行标识符和搜索文本是值；表名、列、运算符和排序方向会改变语句结构。
2. 通过驱动或 ORM 支持的 API 绑定每个可变值。使用该 API 的占位符语法，不给占位符加引号，并单独传递值。对已经插值的语句做预处理并不能修复它。对于长度可变的列表，使用集合绑定，或者只生成占位符，再分别绑定每个元素。
3. 尽可能固定结构。将允许公开选择的每个结构选项映射到该查询的一组有限的、由应用掌控的标识符或完整片段。通过现有的输入错误路径拒绝未知选项。文本看起来像标识符，或对它加引号，都不能证明调用方有权选择某个数据库对象。
4. 保留授权谓词、匹配行为、排序和结果语义。保留有意义的类型和范围校验，但不能用它们替代绑定。不仅要约束存储过程的外层调用，也要将同样的规则应用于原始片段和存储过程内部的动态 SQL。

当执行时的值仍与语句文本分离、可选择的结构只来自该查询允许的映射，且没有引入另一层输入净化时，即可停止。

## 反模式

一个报表在插值前检查名称长度，并手动转义单引号。它会追加任何看起来像标识符的排序输入。这样的校验既没有把值与语法分开，也没有将排序限制为报表批准的列。

## 原因

绑定使数据库 API 能区分数据与使用它的程序。结构映射解决的是另一个问题：在不授予任意语法控制权的前提下，选择允许的查询形态。

## 例外与边界

静态 SQL 没有需要绑定的值，由应用掌控的片段也可以组合。需要时，在从允许的映射中完成选择后，使用驱动提供的标识符处理功能。如果 ORM 和存储过程的原始 SQL 路径拼接了输入，它们也不会自动变得安全。

绑定不会授予行访问权限、限制查询成本，也不会让 `LIKE` 通配符变成字面字符。保留现有搜索契约；当契约承诺字面匹配时，单独转义模式元字符。校验和数据库权限仍是独立的控制措施。

## 示例

一个发票报表使用不加引号的 `%s` 占位符，通过 Django `cursor.execute()` 的值列表绑定客户引用和租户 ID。它对外提供的两个排序名称映射到固定的 `issued_at` 和 `total_amount` 片段，并保留既有方向和同值排序规则。未知排序名称会被拒绝；存储过的单引号仍是普通值，发票可见性保持不变。
