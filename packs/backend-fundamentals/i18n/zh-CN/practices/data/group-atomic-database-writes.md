## 何时应用

当多次本地数据库写入构成一个全有或全无的结果时应用，例如订单及其必需的明细行。应选择这一业务边界，而不是默认将整个请求或一组各自可独立接受的操作包装在一个事务中。

## 指导

1. 明确本地不变量以及维持它所必需的写入。检查一条语句是否已经提供所需原子性；仅将部分持久化会造成无效结果的变更组合起来。
2. 使用仓库现有的事务 API，并将其绑定事务的客户端或上下文传递给每个参与调用。`BEGIN`、所有组合写入和 `COMMIT` 必须使用同一个已借出的连接；独立的连接池查询不会自动加入该事务。
3. 只有每次必需写入和预期受影响行数检查均成功后，才进行提交。发生失败或前置条件未满足时，回滚整组变更并向上传递失败。不要吞掉失败的语句，并将部分完成的操作描述为已完成。
4. 事务清理之后，通过连接生命周期所有者归还连接。如果回滚失败或连接已损坏，应通过驱动丢弃该连接，而不是将不安全的状态归还。
5. 将事务限制在必需的数据库工作之内。不要在保持事务开启时等待用户输入，或远程支付、电子邮件、存储操作，也不要将这些效果描述为受本地回滚保障。

当每次必需的本地写入都共享一次提交或回滚、必需的前置条件均已检查，且不会将部分结果报告为已完成操作时，即可停止。

## 反模式

订单插入通过连接池辅助函数提交，随后明细行插入分别提交。第三行失败，但处理器仍返回订单 ID 并表示成功。下游工作看到的是一个从未完成的订单。

## 原因

事务使其组合变更作为一个整体持久化并变得可见。这一保证只适用于实际在该事务中执行的语句，而不适用于其周围的应用调用或无关连接。

## 例外与边界

单条语句本来就运行在 PostgreSQL 事务中。如果允许部分进展，独立的导入条目可以有意分别提交。保存点可隔离真正可选的工作，但不能把必需工作的失败变成成功。回滚时，序列值可能仍已被消耗。

仅有原子性并不能防止基于陈旧读取的读改写竞争，也不能协调远程效果。保留现有的并发控制，并说明这些限制，而不必为本次分组变更要求新的隔离级别或远程协调设计。

## 示例

某库存调整使用 `UPDATE ... SET quantity = quantity + $1 ... RETURNING quantity` 增加数量，要求返回一行，并在同一个事务客户端上插入审计记录。如果审计插入失败，两项变更都回滚，调用方收到失败。之后的通知不属于这一数据库保证的范围。
