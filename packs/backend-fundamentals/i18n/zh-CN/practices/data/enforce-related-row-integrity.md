## 适用场景

当引用必须在端点、导入、作业和维护 SQL 中都指向真实的父记录时应用。决定允许的关系和移除父记录时的结果，而不只是判断查询能否找到父记录。

## 具体指导

1. 定义完整的父记录身份，以及该关系是否必需。当子记录和父记录必须属于同一租户时，将租户身份纳入其中；两个互不关联的外键可能允许不匹配的组合。
2. 为对应的父记录主键或符合条件的唯一键添加具名数据库外键。匹配列顺序并使用兼容的类型；对必填组成部分要求 `NOT NULL`。即使预先查询可以改善反馈，也要保留数据库约束。
3. 有意识地规定缺失值的含义。PostgreSQL 通常会在任一引用组成部分为空时跳过复合外键检查。对于必须全部存在或全部缺失的可选元组，使用 `MATCH FULL`。对于必填租户加可选父记录 ID 的情况，保持租户非空，并按照预期的关系语义，只允许父记录组成部分缺失。
4. 根据对象生命周期规则选择删除和键更新动作。当引用必须保留独立对象时，拒绝移除；仅对本应一同消失的依赖对象使用级联。将引用置空必须满足其余约束，不能把必填的租户键置空。
5. 依据已批准的修复或保留决定，处理现有孤立记录和不匹配的租户组合。安排迁移期间的约束生效方式，确保在线写入方无法重新生成这些问题。仅将预期的关系违反转换为约定结果；执行更多 SQL 前，先恢复失败的事务状态。

当所有常规写入方都受关系约束、现有行有安全的过渡路径，且父记录移除或重新分配有明确、可强制执行的结果时，即可停止。

## 反模式

一个 API 找到了项目，随后维护作业删除了该项目，API 才插入任务。一次导入还接受了另一个租户的项目 ID。这两条路径都没有在数据库中强制约束完整关系。

## 原因

外键在子记录变化和被引用的父记录变化时维护身份匹配。应用层观察会留下并发间隙，也无法约束绕过执行观察的处理函数的写入方。

## 例外与边界

历史快照或外部标识符可能有意在没有存活的本地父记录时继续存在；不要违背这一契约。有效引用既不代表调用方获得授权，也不保证每个父记录只有一个子记录，甚至不保证存在子记录。软删除会保留父记录行，因此仅靠外键无法强制执行父记录必须处于活动状态的规则。

## 示例

任务要求 `(tenant_id, project_id)`，并按该顺序引用项目表中的唯一字段对。外键使用 `ON DELETE RESTRICT`，因为任务必须保留到被明确处理为止。导入不能将一个租户与另一个租户的项目配对，并发的项目删除也不能悄然使任务失去父记录。调用方权限仍需单独决定。
