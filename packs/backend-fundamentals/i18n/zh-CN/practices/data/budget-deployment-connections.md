## 何时应用

在选择连接池限制，或修改可同时存在的数据库使用进程数量时应用。较小的本地连接池并不代表整个部署的连接上限。应确定部署如何适配分配给它的数据库容量，以及该配额用满时调用方应如何处理。

## 指导

1. 在扣除其他服务、任务、迁移以及管理或预留容量后，确定数据库可用的连接配额。将 `max_connections` 视为上限，而不是数据库能够高效执行同等数量活跃查询的证据。
2. 统计每个实例内的进程、最大副本数、后台工作进程以及滚动部署重叠期间同时存在的连接池。对于直连，将各连接池上限乘以其最大同时存在的进程数，再求和；使总量保持在配额之内。
3. 如果部署使用多路复用代理，应将其客户端连接与面向数据库的连接池分别规划预算。使用实际部署模式的限制和会话亲和规则，而不是假设每个客户端都占用一个后端连接，或假设多路复用不受限制。
4. 根据配额和操作的延迟需求，设置连接池上限和有界的连接获取等待。饱和时必须产生约定的超时或过载结果，而不是无界排队或在连接池之外额外创建连接。确认超时覆盖排队获取连接的过程；查询超时和被放弃的 promise 不一定会终止该等待。
5. 拓扑或连接池限制改变时，重新检查计算。扩大连接池之前，利用观测到的占用量、等待、查询耗时和数据库负载，区分配额耗尽与工作效率低下。

当最大同时需求符合明确的配额，并且在实际部署的驱动和代理配置下，饱和时的连接获取具有有界结果，即可停止。

## 反模式

每个副本允许二十个连接，因为本地看起来不多。自动扩缩容和滚动部署重叠将该设置成倍放大，超出服务配额，而请求却无限期排队。

## 原因

每个连接池都在竞争共享的数据库容量。更大的连接池可能只是将等待转移到已过载的数据库，而不提高吞吐量；部署层面的计算能在这种乘数效应成为生产限制之前揭示它。

## 例外与边界

不存在通用的连接池大小、CPU 公式或连接内存估算。直接建立的维护连接仍消耗容量，但不需要连接池层。本实践规划需求与等待预算；已获取客户端的安全归还或丢弃属于独立的所有权职责。

## 示例

某 API 在计入其他使用者后获得 72 个直连配额。最多同时存在六个 API 进程，已包含滚动部署重叠。每个连接池上限为十个，允许共六十个连接，且有界的获取等待处于请求预算之内。增加副本时需要重新审视这些条件，而不是照搬相同的连接池设置。
