# 不要让安全读取承载所请求的变更

## 何时应用

当选择或更改 HTTP 读取路由、链接或预览背后的行为时应用。判断获取操作是否请求业务变更，而不是判断实现是否执行了任何写入。

## 指导

1. 独立于路由名称，说明所请求的效果：获取一个表示，还是更改业务状态。应包括由查询参数选定的操作，以及渲染期间调用的辅助函数。
2. 保持 GET 和 HEAD 不承载所请求的业务变更，包括取消、批准、确认和消耗一次性令牌。将操作放到明确的非安全操作之后，例如既有的 POST 操作或适当的资源更新方法。
3. 追踪链接预览、预取、爬虫和重复获取所使用的服务端路径。它们都不能仅因获取 URL 就执行业务操作。隐藏链接或更改按钮，无法修复执行变更的读取处理器。
4. 区分安全性与幂等性。重复取消可能保持相同的最终状态，但第一次执行仍然改变了业务状态。单独选择变更重放行为；幂等操作并不会因此变得适合 GET。
5. 将现有业务操作迁移到显式变更路径，并更新所有调用方。不要将旧 GET 保留为会执行变更的兼容别名。在不执行所请求业务操作的情况下，可以保留获取时的附带行为，例如访问日志或普通缓存填充。

当 GET 和 HEAD 只获取信息而不请求业务变更，操作使用显式变更路径，并且调用方不再依赖会执行变更的读取时，即可停止。

## 反模式

`GET /orders/42?cancel=true` 在渲染确认信息之前取消订单。当邮件扫描器跟随链接、在客户操作之前就取消订单时，称其为幂等并无帮助。

## 原因

安全方法允许自动化获取。将业务操作放在这些方法背后，会让预览和预取行使原本只应由用户有意操作行使的权限。

## 例外与边界

安全不意味着没有副作用或可以公开访问：附带的日志和缓存可以保留，访问检查仍然适用。敏感搜索可以使用 POST，以免输入出现在 URI 中。本实践不决定变更重试、幂等性存储或 CSRF 策略。

## 示例

`GET /orders/42/cancellation` 显示已获授权的客户订单及确认表单，不取消订单，也不消耗操作令牌。表单提交到 `POST /orders/42/cancellation`，由其检查操作权限并执行取消。之后的 GET 显示结果；HEAD 读取元数据而不执行操作。
