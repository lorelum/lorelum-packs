## 何时应用

当其他来源的浏览器脚本需要访问响应时应用。确定允许哪些站点，以及使用哪种凭据模式。CORS 错误并不能证明服务端拒绝了请求或阻止了其产生效果。

## 指导

1. 为端点声明接受的来源和凭据模式。将完整序列化的来源（包括协议和端口）与应用自行管理的来源集合匹配；不要使用子串匹配或任意回显。除非针对客户端策略的适用范围已有清晰、有限的理解，且确实有意要求支持，否则将 `null` 视为不可信来源。
2. 对携带凭据的访问，在 `Access-Control-Allow-Origin` 中返回单个被接受的来源，并返回 `Access-Control-Allow-Credentials: true`。绝不能将凭据与来源通配符组合使用。对于有意公开、不携带凭据的访问，`Access-Control-Allow-Origin: *` 是合理的。不要为修复某一项集成而全局启用凭据。
3. 通过现有 CORS 机制处理预检，不要要求 `OPTIONS` 携带会话 cookie。允许预期的来源、方法和请求头；对于携带凭据的访问，应显式列出方法和请求头。预检允许的是浏览器继续发出请求，而不是批准操作本身。仍应按正常方式对实际请求进行身份认证和授权。
4. 为实际响应应用相匹配的访问头，包括希望被接受的客户端能够读取的错误响应。只有预检头并不能让最终响应可被访问。仅在需要时暴露额外的响应头。对于不接受的来源，应省略访问许可，而不是回显其值。
5. 当响应头随请求来源变化时，将 `Origin` 合并到 `Vary` 中，包括拒绝来源或没有来源的响应变体，并保留现有成员。如果中间层缓存预检响应，应区分其他会影响其决定的请求输入，或禁用这种缓存。不要将浏览器预检缓存与普通 HTTP 响应缓存混为一谈。

当预期的浏览器客户端只获得已声明的响应访问权限、任意来源都无法获得许可，并且预检与实际响应实施同一策略时，即可停止。

## 反模式

中间件将任意 `Origin` 复制到允许来源的响应头中，并启用凭据。这样，恶意站点的脚本就能读取已登录用户的账户响应；用回显替换 `*` 并没有建立信任边界。

## 原因

浏览器根据响应头判断发出请求的哪些脚本能够访问响应。携带凭据的来源回显会将这种访问权限扩展到攻击者控制的站点。

## 例外与边界

同源客户端不需要 CORS 许可。CORS 不会授权服务端操作，不会保护基于 cookie 的写入免受 CSRF 攻击，也不会限制伪造或省略 `Origin` 的非浏览器调用方。即使客户端已被允许，cookie 和浏览器隐私策略仍然适用。响应访问权限随来源变化，并不能隔离已缓存的个性化响应体。

## 示例

一个门户仅允许来自 `https://console.example` 的携带凭据的读取，返回该来源及 `Vary: Origin`，并保留实际端点上的授权检查。另一个公开汇率数据接口使用通配符，不携带凭据。两个路由都不把其 CORS 策略视为写入保护的替代品。
