## 何时应用

当 HTTP 适配器将拒绝或意外失败转换为响应时应用。表达操作已经决定的结果；不要在错误序列化器中选择恢复行为。

## 指导

1. 阅读现有的状态、响应头、媒体类型和错误响应体契约。保留其错误结构及稳定标识，而不是引入新的封装结构或暴露异常消息。
2. 将实际情况映射到其 HTTP 含义：在适用时，区分无效输入、缺少凭据、访问被拒绝、资源不存在、冲突和服务端失败。保留既有的不披露策略，包括对被隐藏的资源返回 404。确保响应体中的任何状态都与 HTTP 状态一致。
3. 保留必需响应头和方法语义。401 需要适用的 `WWW-Authenticate` 质询；405 需要 `Allow`。HEAD 错误不包含响应内容。不要仅为简化调用方而将失败变成 200 响应。
4. 仅返回契约允许的、安全且有助于采取行动的细节。不要在响应体和响应头中包含 SQL、堆栈跟踪、内部路径、其他租户的数据和敏感的提交值。绝不记录凭据、令牌或连接密钥，即使是在受保护的日志中。通过现有受限通道记录诊断原因之前，先清除敏感内容；若已有可用的关联引用，则保留它。
5. 对外以通用信息表达意外失败。仅在 `Retry-After` 能准确描述实际情况时添加该响应头；无论该响应头还是错误序列化，都不会使重放变得安全。

当失败保留了真实的状态与必需响应头、既有客户端协议，以及安全的对外细节，并且诊断信息不含秘密时，即可停止。

## 反模式

包装器对每个异常都返回 `200 {"items": [], "error": str(error)}`。身份认证失败看起来像空集合，而数据库异常则可能暴露连接凭据。

## 原因

客户端和中间层会独立于 JSON 解释状态与响应头。准确的语义有助于正确处理，同时无需将私有异常细节变成 API 的一部分。

## 例外与边界

保留既有的 GraphQL 传输层／应用错误语义，而不是强行给每个应用错误套用 REST 风格状态。有效的空结果仍然是成功。本实践既不增加重试，也不引入新的错误封装结构、恢复策略或遥测系统。

## 示例

某 API 已使用 `{"error":{"code":"...","message":"..."}}`。订单冲突返回 409，错误码为 `order_state_conflict`；意外的数据库失败返回 500，错误码为 `internal_error`。后者仅在移除凭据、令牌和连接密钥之后才使用现有受限诊断记录，并且不改变响应模式。
