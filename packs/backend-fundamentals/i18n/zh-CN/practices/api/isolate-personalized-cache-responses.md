## 何时应用

当修改某个端点的 HTTP 缓存行为，而该端点的表示取决于调用方时应用。源站上的正确权限检查，无法保护后续那些未到达该处理器便已得到应答的请求。先确定是否允许存储，再确定新鲜度。

## 指导

1. 对实际响应体、响应头、重定向和错误进行分类，包括匿名、已认证和租户变体。追踪那些能在应用代码运行前就应答的共享缓存；仅有 cookie 和 `Set-Cookie` 并不能禁止 HTTP 缓存。
2. 当允许浏览器存储时，使用不带字段限定的 `Cache-Control: private` 将个性化响应排除在共享存储之外。当私有和共享 HTTP 缓存都不应保留这些响应时，使用 `no-store`。`no-cache` 允许存储，但要求在复用前成功验证。为每一条相关响应路径设置策略。
3. 为真正公开的表示设置有意选择的新鲜度策略，使其可以缓存。不要在这种表示中附加个性化字段。携带 `Authorization` 的请求受到特殊的共享缓存限制，但 `public`、`s-maxage` 或 `must-revalidate` 等指令可能允许复用；不要不加区分地将它们加入已认证的响应。
4. 将所有用于选择表示的请求头纳入 `Vary`，保留现有成员，并使中间层的缓存键与这些输入一致。`Vary` 无法指明内部主体或租户变量。有意采用受保护的共享缓存时，需要可信的身份分区、每次命中前的权限检查，以及明确的撤权策略；由客户端自行声明的租户请求头或仅含 URL 的键都不够。否则，应保持私有缓存或不存储。
5. 更改策略时要处理已存储的条目：通过已部署的缓存机制，使不安全的共享变体过期或将其清除。新响应头不会撤回旧的、仍然新鲜的条目。重新验证及验证器必须保持在同一表示边界内。

当每个响应都有明确的存储决定，并且没有共享缓存命中能够越过其预期受众或表示边界时，即可停止。

## 反模式

一条边缘规则按路径缓存 `/dashboard` 五分钟。源站正确选择了已登录客户的账户，但下一位客户的请求在未执行授权检查的情况下收到了第一位客户的响应。

## 原因

新鲜的缓存命中可以完全绕过源站逻辑。存储限制和正确的选择键，可以防止复用扩大原本合法响应的受众范围。

## 例外与边界

公开资源不需要一律禁止缓存。`private` 控制的是存储位置，而不是加密，也不是同一浏览器内不同应用账户之间的隔离。`no-store` 并不保证能够防范恶意缓存、浏览器历史或独立应用存储带来的隐私风险。两种指令都不能替代对目标资源的授权。

## 示例

账单摘要使用 `no-store`；非敏感的个人偏好读取允许私有存储。匿名商品目录仍然允许共享缓存，并使用 `Vary: Accept-Language`，因为语言会改变其表示。登录不会悄然向该公开变体添加账户专属价格。
