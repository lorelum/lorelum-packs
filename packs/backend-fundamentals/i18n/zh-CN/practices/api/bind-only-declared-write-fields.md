## 何时应用

当请求体、表单或补丁会转化为持久化属性时应用。合法的记录编辑者仍可能无权指定记录的所有者、角色、余额或生命周期状态。应独立判断字段是否允许赋值，而不是依据提交值看起来是否合法。

## 指导

1. 为此操作及调用方能力声明可写属性。当契约不同时，将创建、编辑和特权命令分开。除非策略明确允许赋值，否则所有权、租户、计算得出的金额、角色授予和工作流元数据均由服务端掌控。隐藏的控件和响应模式都不是写入策略。
2. 在持久化绑定之前，构造专用输入对象或显式字段投影。只包含已声明的字段；之后绝不能再展开原始请求体，也不能先绑定完整领域模型。根据现有 API 契约拒绝或忽略未声明的输入。拒绝列表会使未来新增的属性暴露在外。
3. 在每一层可赋值结构上应用该投影。允许一个地址对象，并不等于允许其中任意的账户元数据。对于补丁协议，应检查目标路径，以及所有可能复制受保护值的源路径，包括替换父级的情况。防止其他编码形式、批量处理器或嵌套关系更新绕过同一写入契约。
4. 从可信上下文或计算中取得由服务端掌控的赋值。在局部更新时保留被省略的字段，并按现有语义区分清空与未提供。验证已接受的值，但不要把类型正确的角色或有效的所有者 ID 误当作赋值权限。
5. 显式处理委托变更和管理变更：在绑定之前选择其获准使用的字段策略，或使用现有特权命令。记录编辑权限并不开放所有字段；针对普通编辑者的限制，也不能意外禁止原本有意支持的转移操作。

当每一项持久化的客户端赋值都属于所选写入契约，包括嵌套及其他变更路径，并且未声明字段不会因模型扩展而变得可写时，即可停止。

## 反模式

个人资料处理器加载一个已获授权访问的账户，验证已知 JSON 类型，然后将整个请求体传给 ORM 更新方法。新增的 `role` 属性因为存在于模型中而被接受；对目标记录的所有权检查从未限制这项赋值。

## 原因

持久化模型暴露的状态，比某个具体客户端操作应当控制的状态更多。显式列出允许字段的投影，能让新模型属性在被有意纳入之前保持不可写。

## 例外与边界

这里处理的是字段是否允许赋值，而不是新增验证层或资源授权方案。有意允许任意内容的元数据映射可以在其隔离的命名空间中接受任意键，但不得将这些键合并到特权属性中。可读不意味着可写。

## 示例

账户编辑命令仅投影 `displayName` 和 `address.city`，并从可信上下文获取租户。提交的 `balance`、`ownerId` 或 `address.role` 永远不会进入赋值环节。单独的、经过授权的转移命令接受其声明的新所有者字段，而不扩大普通编辑契约的范围。
