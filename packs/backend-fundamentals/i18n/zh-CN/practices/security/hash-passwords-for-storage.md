## 何时应用

当应用负责登录密码认证时应用。存储能够支持身份认证的验证值，既不保留可恢复的密码，也不让数据库被盗后的离线猜测变得廉价。密码强度、会话和资源权限是独立的判断事项。

## 指导

1. 明确管理责任。如果可信身份提供方管理密码，就保留其支持的身份关联，而不是再收集一份密码副本。不要为仅使用身份提供方的应用引入本地密码存储。
2. 使用持续维护的高层密码哈希库。对于支持的新系统，优先选择 Argon2id；只有在适用的部署或合规约束及当前 OWASP 指引下，才选择其他专用算法。绝不要用通用摘要或自定义密码学构造替代。
3. 让库为每个密码生成安全的随机盐，并存储其支持的编码验证值，包括算法、盐和成本参数。不要为登录或恢复而保留明文或可逆副本。固定的共享盐并不够。
4. 根据有文档记录的安全基线选择成本，并评估部署内存与预期认证负载。保留参数来源，而不是复制未经解释的迭代次数。遵循文档规定的输入限制，不要静默截断密码。注册、重置和更改必须使用同一存储策略。
5. 通过库的验证 API 进行验证；不匹配时认证失败。不要生成一个新的加盐哈希再比较字符串。验证成功后，使用受支持的重哈希检查，按当前策略升级过时的验证值；如果迁移不安全，则使用既有的重置路径。不要将密码和验证值放入响应和日志。

当每次本地密码写入都只存储受支持的验证值，登录使用其验证 API，且成本和升级都有明确依据时，即可停止。

## 反模式

注册时存储 `SHA256(password)`，重置时却加密密码，以便支持人员恢复。前者允许低成本离线猜测；后者在密钥泄露时暴露可恢复的密码。添加共享盐并不能提供专用的自适应密码验证值。

## 原因

离线猜测绕过了在线速率限制。专用密码哈希会提高每次猜测的成本，而唯一的盐能防止在多个账号间复用同一次计算。编码参数支持验证和日后升级，但无法让弱密码变得不可猜中。

## 例外与边界

受支持的替代方案有不同的成本和输入约束：scrypt、既有的 bcrypt 或经过 FIPS 验证的 PBKDF2，都不能盲目沿用 Argon2id 设置。现有弱哈希需要迁移或重置，而不只是让新注册更安全。高熵令牌和需要可恢复的集成密钥是不同的存储问题。可选的 pepper 不能代替盐或专用哈希。

## 示例

某服务使用 `argon2-cffi` 的 `PasswordHasher`，并采用有文档记录且适合部署环境的参数配置。注册和重置存储 `hash(password)`；登录调用 `verify(stored_hash, candidate)`。成功后，由 `check_needs_rehash` 决定是否升级。仅使用 SSO 的账号保留提供方关联，不保存本地密码。
