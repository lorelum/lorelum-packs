## 何时应用

新增或更改已签名的 Webhook 接收器，或读取其请求体的中间件时应用。在事件声明驱动应用行为前，依据提供方规则确认其真实性。HTTPS、看似合理的 JSON 和签名头的存在，都不能认证传入消息。

## 指导

1. 从可信路由和设置中确定提供方与端点配置。遵循该提供方的验证约定：签名所针对的表示形式及请求头、端点密钥或公钥、接受的版本，以及必需的新鲜度检查。不要套用另一个提供方的 HMAC 格式或请求头名称。
2. 在适配器、中间件和代理的整个传递过程中，保留该验证器要求的原始表示形式。Stripe 要求未经修改的原始请求体字节和 `Stripe-Signature`；解析 JSON 后再序列化，无法重建这些字节。防止通用请求体中间件替换所需输入。
3. 如果提供方提供持续维护的 SDK 验证器，就使用它，并传入对应端点和环境的正确验证材料。Stripe 的 Webhook 签名密钥不是其 API 密钥。保留受支持的新鲜度检查。手动验证必须准确实现文档规定的签名输入、格式、版本、比较方式和新鲜度语义。
4. 让所有事件驱动的副作用都以验证成功为前提：记录变更、可触发实际工作的队列、外部调用和已处理事件标记。签名无效或消息格式错误时，终止处理并返回适合该提供方的失败响应。修复请求体或配置错误，而不是接受未签名输入。
5. 分派验证成功后由验证器返回或接受的事件，而不是之前解析的副本。真实性确认后，仍保留事件类型、账号、资源和业务检查。不要将验证密钥放入响应和日志。

当事件驱动的操作必须使用所需原始输入和正确端点配置，通过提供方专用验证后才能执行时，即可停止。

## 反模式

处理器根据解析后的 `invoice.paid` JSON 激活订阅，然后才记录签名失败。即使把检查提前，如果验证的是重新序列化的 JSON 而不是 Stripe 签名的字节，仍然有问题。为了恢复服务而接受未签名消息，会彻底移除真实性保障。

## 原因

攻击者即便没有签名材料，也能模仿事件字段。验证会将所需的消息输入与配置的发送方绑定；在副作用发生之后验证，无法撤销已经给予伪造声明的信任。

## 例外与边界

SDK 可以将解析与验证结合；只要原始输入得以保留，并且不信任任何未经验证的字段，解析本身并非禁止行为。终结签名验证的中间层需要经过认证且保留来源信息的交接，而不是客户端设置的“已验证”标记。有效签名并不能证明消息此前未出现、顺序正确、目标获准或当前状态符合要求。重试仍需要既有的重复投递处理；签名不是稳定的去重键。

## 示例

某 Stripe 路由保留原始字节，并使用 `Stripe-Signature` 和该端点的签名密钥调用 SDK 的事件构造验证器。失败时在任何订阅或账本变更之前退出。只有返回的已验证事件才会进入既有发票处理器，并继续接受其账号和重复投递规则的约束。
