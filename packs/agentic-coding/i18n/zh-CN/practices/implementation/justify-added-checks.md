# 新增检查前先说明理由

## 适用场景

**在决定新增或加强检查之前使用，不要等实现后的评审才判断。**
规划时使用，普通任务中 Agent 自行提出防护措施时也使用。任务不必提到门禁、重复或成本。
第一次增加的检查，即使没有重复任何工作、没有让主路径无法完成，也可能缺乏理由。

## 具体指导

1. 说出拟加检查要阻止的失败：什么实际输入、调用方、状态变化或故障能到达这个操作，谁会受损。
   单独列明强制契约或政策；泛化的风险类目不是失败路径。
2. 找到保障负责人和既有覆盖。确认入口校验、生产方后置条件、授权、事务、安装或发布已经建立
   什么事实，哪些情况会在使用前使它失效。本机地址、类型转换或早前检查本身，都不能证明保障持续有效。
3. 说明额外保护：没有这项检查，哪个仍可达的失败会漏过去？区分新的信任、转换或并发状态边界，
   与同一规则的又一份副本。安全或数据丢失风险尚不明确时先调查，不要把未知当作不存在。
4. 比较额外保护与检查自身的影响：误拒绝、延迟与 I/O、维护、服务不可用，以及启动、升级、停止或
   修复受阻。实际成本可能改变选择时做有界观察；不要求例行 benchmark 或风险报告。
5. 新增或保留必要保护；否则收窄范围、选择足够的非阻断响应、仅在维持所需保障时调整执行时机，
   或不加检查。在现有设计或评审中简要记录理由。目标不是检查更少。

在实施之前，明确这项拟加检查的取舍即可停止。如果必要性已确定，只剩归属位置未定，使用边界
所有权决策；如果需要把多项有理由的检查组合成可用工作流，走查验收路径，不重复这项决定。

## 反模式

普通后端任务让 Agent 为每次启动增加整个模型目录的哈希扫描，为每个受控 HTTP 响应增加完整业务
schema 遍历，为修复增加健康服务探针。每项都被称作更安全，却没人指出它们比选定模型的 loader、
响应生产方的已确立契约，或修复自己的身份与权限检查多保护了什么。无关文件拖慢启动，有效结果
多了一套拒绝规则，服务故障时修复反而不能运行。只在实现完毕后逐项评审，错过了更早的取舍时机。

## 原因

看似合理的防护可能增加工作和拒绝路径，却没有补上真实缺口。把必要性独立为一个决策，能在 Agent
采纳提案之前检查它；之后把检查放对位置、证明主路径可通，都不能回答最初是否应该增加它。

## 例外与边界

必需的安全、数据一致性和契约是取舍约束；成本高不授权删除。保留外部输入检查、资源专属授权、
并发状态的原子保护、必需的 native/model 质量与发布完整性，以及恢复身份保障。有独立理由的纵深
防御仍然有效。已接受的检查契约须由其负责人按正常流程修改，不能悄悄把失败降为警告。

本条不是生产旁路、新的用户审批要求，也不是全面禁止启动扫描。可变的导入模型可能需要不可变
安装不需要的验证。修复操作可以不依赖业务就绪，但仍须建立自己的授权、身份和修改安全条件。
类型和契约测试不能替代真实信任边界。

## 示例

任务把桌面客户端接到随附的本机 worker。worker 构造已验证记录，会话已认证，响应在序列化后
不会再变。Agent 在增加第二次完整业务 schema 遍历之前，找不到它能捕获的新失败，因此不加；
解码、协议匹配、身份和请求关联仍保留。公开导入入口仍须验证任意 JSON，不能继承随附 worker 的保障。

只读桌面启动准备第一次增加磁盘剩余空间门槛，理由是以后也许会增加导出。它没有重复检查，也没有
引入依赖循环。Agent 在编码前否决：启动没有大量写入，已接受的契约也不要求这个门槛，受支持的
只读会话会多一条拒绝理由，却没有新增保护。必需的启动输入、native/model 和发布完整性检查仍保留；
可变模型仍须防护验证与使用之间的变化。
