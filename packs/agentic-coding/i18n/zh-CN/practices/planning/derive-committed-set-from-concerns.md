# 从关切推导承诺集

## 适用场景

任何将用于做出未来判断的集合正在构建时适用：计划任务、验收或完成标准、评审规范、测试清单、校验或权限规则、打分维度。判断标准是功能而非名称：查询该集合会决定通过与否、做还是缓、允许还是拒绝、或给出分数，就适用本条。第一次提出条目时、之后任何增删时、以及接手已经堆大的集合时（先倒推其关切）都适用。只记录或探索的列表——笔记、盘点、大纲——不触发。它也覆盖团队口语描述的那些情形：一份不断变长直到挡住一切的检查单、一个总有人往上加的完成标准、一份条目重叠到各自失去分量的打分表、或一份已经看不出什么才真正必需的计划任务清单。

## 具体指导

先写下集合要服务的关切：当前验收必须区分的结果、有证据可达的失败、以及有权限者明确指名的扩展。条目只能从关切推导而来。候选条目过三问：它服务哪个尚未被覆盖的关切；有它在场哪个判决会不同——计划是做还是缓、检查是收还是拒、打分是分开哪两份合理产出；是否已有条目在测同一件事。重叠就合并，而不是两条都留。为命名张力记录选定的工作点：覆盖与稀疏、当前要求与指名扩展、保护与可用。讨论中提出的条目先翻译成关切；改变不了任何判决的条目搁置，不加入。接手堆大的集合时，从现有条目倒推关切，再重新推导并删掉无主条目。当每个关切都有条目、每个条目都改变某个判决、无未合并重叠、每条的失败语义已定时停止并冻结；此后新条目必须携带新关切。小到无需计划的任务，关切集就是目标句加验收，推导是平凡的。

## 反模式

团队的数据迁移评审规范从三条检查起步。每次事故都增加一条听起来合理的新标准，直到每个迁移都被什么东西挡住、几周时间耗在争论例外上。随后一刀切清理，规范又漏掉了最初引发它的那类失败。条目数在两个方向都被调过，而其背后的关切集从未被写下。

## 原因

每一条加入都局部有理，每一条删除都局部有代价，所以无人管理的集合会一直生长，直到集合本身的大小成为失败。条目数是派生量：修复不公意味着增加一个关切，修复稀释意味着合并一个关切，直接调整条目只会产生摆动。

## 例外与边界

治理契约、政策或合规要求可以强行加入一个说不出本地关切的条目；注明来源并保留。探索性列表可以保持非承诺草稿，直到需要决策性集合。本条负责形成集合；已组装计划的路径是否走得通靠走一遍判断，工作是否有当前理由在准入时判断。

## 示例

团队定义 schema 迁移上线前必须通过什么。关切：变更可回滚、存量数据必须存活、失败可观察。推导出四个条目：经过测试的回滚路径、迁移行的完整性检查、切换期写失败告警、中止条件。评审者提出第五条——迁移文件的风格检查——被搁置：没有关切认领它，它也不改变任何"继续还是中止"的判决。
