# 保持验收路径可完成

## 适用场景

规划或实现包含多项检查的工作流、需要让它们组合后仍可完成时使用。走查正常操作、启动、停止及受支持的修复或恢复命令，即便任务没有提到门禁。完整性和新增摩擦都覆盖必需路径，包括错误、重复和重开场景。单项拟加检查是否必要，由 `justify-added-checks` 决策回答；本条判断如何组合检查而不使已接受的工作流失效。

## 具体指导

把每条验收条件写成从发起动作到可观察结果的有序步骤，包含变更加入的每个检查。先走所有条件查完整性：没有 owner 的必需步骤是映射缺口，先补再谈轻重。再走必需路径查摩擦：每个能拒绝、拖延或要求干预的新增检查都是闸门。给每道闸仍能拦住可指名失败的最低档——observe（记日志）、mark（在结果上标注）、confirm（问一次，且在触发处有人能回答）、block（拒绝）。高于 observe 的档位只能由本部署事实或契约中存在的演员和路径支撑；风险类目名或泛化的攻击者什么都支撑不了。宁把有理由的闸门收窄到高风险子集，不闸整条路径。做删除测试：说出删掉它具体会坏什么、坏给谁；答不出就删闸。没人能回答的 confirm 就是 block——降档或收窄并给文档化旁路。然后走一次失败：挑最可能失败的那条检查，让它单独失败，说出还有什么活下来；如果单条失败会作废其他所有已满足的条件，要指名谁需要这种严格度、归因式或部分结果会怎样误导。把档位和指名失败记在闸门的计划条目旁。当每条验收条件都能在验收或政策未提名的干预之外完成、且每道闸都指名了其档位拦住的失败时停止。小到无需计划的任务只问：新增检查能否阻断或拖延必需路径，什么失败或强制政策能证明这种影响有必要？保留有理由的阻断，否则降档、收窄或省去检查。

修复命令不应要求损坏索引先恢复健康；停止已确认身份的旧进程，不必要求其业务 API 与新客户端
匹配。保留操作专属授权、进程身份、活动保护和一致性要求。必需保障与恢复契约冲突时，应暴露
冲突，不要为了让命令通过而绕过它。

## 反模式

任务给本地 CLI 加一个 config-set 命令。Agent 连同键 allowlist、路径穿越校验、属主权限检查和每次写入确认一起交付。验收场景——开发者跑命令、配置更新——从此需要请求从未提过的交互和授权，而且调用该 CLI 的脚本无法回答确认。校准在交付之后才到，形式是删代码。

## 原因

逐条审查只看见每道保护的故事，看不见组合后的路径；训练对可见事故的定价高于不可见的不可用性，所以未经走查的计划理性地过度保护。Practice 只改善它指名的维度：完整性、摩擦和失败组合必须各走一遍才各自改善。

## 例外与边界

治理政策或合规可以在没有本地可达性的情况下强制档位——注明政策，闸门保留。真实可达的威胁配得上 block；本条做校准，不移除正当防护。既有系统防护是约束，不是删除测试对象；若它们使验收不可能，上浮冲突而不是移除。检查归属哪层、是否重复，是边界归属问题。

## 示例

config-set 走查把四道检查全开的主路径写下：命令、allowlist、权限、确认、写入、验证。删除测试：穿越输入到不了路径、操作系统已强制文件属主、确认拦截的是验收没提的笔误——全部降级或删除。一个关切带证据存活：覆盖 security-token 键会迫使别处重新认证。闸门收窄为仅该键子集的一次确认；其余键无打扰写入，变更记入日志。

后端修复命令必须能在服务未就绪时重建损坏的派生索引。提议复用的 readiness 预检却会在修复开始前
拒绝这一状态。Agent 为普通查询保留就绪要求，为修复提供单独的授权路径和必需的互斥修改保护。
修复不必先成功查询索引就能重建；未授权调用方或冲突的 writer 仍被拒绝。不引入全局“跳过检查”开关。
